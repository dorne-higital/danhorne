- [x] Temporary/expiring user access (`/admin/users`) — "Create temp access" alongside the existing "Invite user": admin sets an email, password, and expiry directly (no email round-trip needed, works immediately — for handing out quick QA/contractor access). `profiles.expires_at`, `supabase/migrations/0015_temp_user_expiry.sql`. Access is hard-blocked on every authenticated request the instant expiry passes (`requireAdminSession`), independent of any cleanup timing; the actual row gets hard-deleted the next time anyone loads the Users list (no scheduled job in this app, so it's "next visit," not the exact expiry second — the access block is the real security boundary, the delete is housekeeping). A temp account can be turned permanent early via "Make permanent" (clears the expiry). Also fixed a real bug found in the same pass: invite/reset-password emails were generating `localhost` links whenever triggered from a local dev session, instead of the fixed production URL — both now prefer `NUXT_PUBLIC_SITE_URL` over the request's own origin.
- [x] Header CTA made optional/configurable — `/admin/layout` gained a "Header CTA" panel: show/hide toggle, custom button text, and either "open the contact form" (existing modal behavior) or "go to a link" (plain URL, internal or external). `site_settings.header_cta_enabled`/`header_cta_label`/`header_cta_action`/`header_cta_url`, `supabase/migrations/0013_header_cta.sql`. **Run this migration before the site will load** — `/api/settings` selects these columns now, and the header/footer/every page depend on that endpoint.
- [x] Layout picker (`/admin/layout`, sidebar under Site) — pick the header nav arrangement and footer arrangement from a fixed set of styles, no code changes needed. `site_settings.nav_style` (`default`/`centered`) and `footer_style` (`default`/`simple`), `supabase/migrations/0012_layout_settings.sql`. Header nav now reads a menu called `header-main` (renamed from the old hardcoded `main` by the same migration); footer now actually reads menus too — `footer-main` for an extra link column (default style) or inline links (simple style), `footer-legal` for bottom-bar legal links (default style only) — both optional, footer renders exactly as before if neither exists yet. "Centered" nav takes the link list out of flow and centers it on the header itself (`position:absolute; left:50%; transform:translateX(-50%)`), so it stays dead-center regardless of logo/CTA width instead of drifting off-center like a plain flex/auto-margin approach would. Deliberately a fixed set of pre-built styles, not a general theme/CSS editor.
- [x] Activity log extended to everything, plus a real browsing UI — `logActivity()` calls added to the remaining ~15 mutating endpoints (menus, users/invite/role/remove, own-profile edits, uploads, settings, redirects, forms), so `/admin/activity` (tabs by entity type, action filter, debounced summary search, real server-side pagination — `GET /api/activity` now takes `entity_type`/`action`/`search`/`page`/`pageSize` and returns `{ entries, total }`) covers the whole CMS, not just pages. Dashboard's "Recent activity" widget updated for the new response shape and gained a "View all" link. Deliberately **not** logged: automatic redirects created by a page rename (already implicit in the page's own "renamed to X" entry — would be a duplicate), and dismissing a 404 suggestion (housekeeping, not content activity). Settings changes log which _fields_ were touched (colors/site name/logo/etc.), not a full before/after diff — simpler, and the endpoint already had several independent conditional update blocks that don't have one clean "before" snapshot to diff against.
- [x] reCAPTCHA v3 spam protection for the contact form — second panel on `/admin/integrations` (`site_settings.recaptcha_site_key`/`recaptcha_secret_key`/`recaptcha_enabled`, `supabase/migrations/0011_site_settings_recaptcha.sql`). Secret key is write-only from the admin UI — the server never sends its actual value back, only whether one's set. `DynamicForm.vue` loads the reCAPTCHA script only where a form actually renders (not site-wide like GTM, since v3 shows a floating badge), gets a token on submit, and `server/api/forms/[id]/submit.post.ts` verifies it server-side (`server/utils/recaptcha.ts`, score threshold 0.5) before allowing the submission through — on top of the existing honeypot + rate limit, not replacing them. When enabled, a failed/blocked verification (including an ad-blocked script) does reject the submission — that's the standard reCAPTCHA v3 trade-off, not a bug. **Note**: the site key's registered domains (google.com/recaptcha/admin) must include `localhost` for local testing to work at all, separate from the site's actual production domain. The default floating badge is hidden (`app/assets/scss/components/_recaptcha.scss`) — Google's terms require that when hidden, attribution text is shown near the form instead, which `DynamicForm.vue` does (above the submit button, only when reCAPTCHA is active).
- [x] GTM integration that overrides the built-in analytics — `/admin/integrations` (`site_settings.gtm_id`/`gtm_enabled`, `supabase/migrations/0010_site_settings_gtm.sql`). When on and a container ID is set, `app.vue` injects the GTM snippet (never on `/admin` routes) and the first-party pageview tracker (`analytics.client.ts`) checks the same settings and stops firing, so nothing double-counts — turn it off and the built-in tracker picks back up automatically. Server validates you can't end up with `gtm_enabled: true` and no container ID either way round (enabling with no ID set, or clearing the ID while already enabled).
- [x] 404-to-redirect suggestions — real 404s (checked against the redirects table first, so this only fires on genuine dead ends) are logged to `not_found_hits` (`supabase/migrations/0009_not_found_hits.sql`, `server/api/track-404.post.ts`, rate-limited like the pageview tracker). `/admin/redirects` shows a "Suggested redirects" panel above the manual list — path, hit count, last seen, "Create redirect" (prefills the existing New redirect modal) or "Dismiss". Self-cleans: a suggestion whose path is now a live page slug or already has a redirect is filtered out server-side rather than needing every resolving action to remember to delete the hit row.
- [x] Draft/publish state with a real working draft, separate from what's live, plus token-based preview links. `pages.status` (`draft`/`published`, `supabase/migrations/0007_page_draft_publish.sql`) gates whether a page exists publicly at all; `pages.draft_title`/`draft_blocks` (`supabase/migrations/0008_page_draft_content.sql`) hold the working copy the editor edits and Save writes to — **Save no longer goes live**. A separate **Publish** button (`POST /api/pages/:slug/publish`) copies the draft onto `title`/`blocks`, the columns the public site actually renders; a **Publish changes** state on the same button shows when an already-live page has unpublished edits. **Unpublish** flips `status` back to `draft` without touching content. The public `pages/[slug].get.ts` endpoint 404s a never-published page for anonymous visitors unless the request carries a matching `?preview=<preview_token>` (a stable per-page secret, no login needed), and serves the draft instead of live content whenever that token is present — so Preview always shows pending changes, even on an already-published page. Draft pages are excluded from `sitemap.xml`, preview views get a `noindex` tag and a "you're viewing unpublished changes" banner, and preview visits are excluded from analytics tracking. Restore-from-history now restores into the draft (not live) — still requires Publish to go out. SEO fields are deliberately **not** part of the draft/live split (still save immediately via the pages-list SEO modal) — lower stakes than content, not worth the added complexity.
- [x] Page revision history — last 10 saves per page, restore from a "History" panel in the page editor. Snapshots on create/save/duplicate/restore (`server/utils/pageRevisions.ts`, `page_revisions` table). Restore brings back title/blocks/seo only, deliberately not slug/parent — undoing content shouldn't silently move the page's URL.
- [x] Native `confirm()` dialogs replaced with the styled `Modal` — new `ConfirmModal.vue` + `useConfirm()` composable (module-scope state, same singleton pattern as `useToast`), mounted once in `admin.vue`. `confirm(message, options)` returns a `Promise<boolean>` so every delete call site just does `if (!(await confirm(...))) return`, same shape as the old `window.confirm()` call. The unsaved-changes route guard (`useUnsavedChanges.ts`) uses it too — Vue Router awaits a Promise returned from `onBeforeRouteLeave`, so that worked out without any special-casing. Added a `.danger` button style (red, for delete/remove confirms) to `_buttons.scss`. The native `beforeunload` prompt in the same file is untouched — browsers force that one, it can never be styled.

Replaced at all ~21 call sites; also dropped the now-unnecessary `: any` on each `catch` since the helper takes `unknown`. Left `useUploads.ts`'s two catch blocks alone — those use `describeUploadError()`, a different, upload-specific helper, not this pattern.

Admin-gated routes were left as-is since only trusted logged-in users see those.
- [x] Form submissions rate-limited — `server/utils/rateLimit.ts` is an in-memory sliding-window throttle (5 submissions per 15 min per IP, across all forms), checked in `server/api/forms/[id]/submit.post.ts` before the DB lookup. It's in-memory rather than DB-backed, so it resets on a cold start and isn't shared across concurrent serverless instances — a determined/distributed spammer can get around it, but it stops the actual threat described (a script hammering the endpoint in a loop) without new infra, which fits a low-traffic personal site.
